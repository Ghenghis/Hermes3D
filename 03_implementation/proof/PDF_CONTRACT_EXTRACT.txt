Hermes3D OS Production Wiring Contract Kit
Executive summary
The provided screenshots depict a much larger , later-stage shell than the code currently present in the
uploaded Hermes3D-7.zip. Inspection of the archive shows a smaller , earlier React shell with 13 routes, a
mock-only settings tab, three live bridge reads (/api/printers, /api/plan/preview, /api/
providers/health), nine adapter schemas, and a partial external-tool registry. By contrast, the
screenshots show a broader Source OS shell, 58 visible source modules, many install/setup buttons,
proof actions, planner controls, provider cards, and plugin cards. The consequence is straightforward: the
GUI is mostly representational because the runtime contract between card → manifest → installer →
detector → launcher → health/proof gate is still missing or only partially implemented in the uploaded kit.
That is the core gap. 
A production-grade contract kit for Hermes3D OS should therefore be built around a single manifest-driven
app runtime. Every visible card, button, tab, and provider must resolve to one canonical manifest entry, one
installation strategy, one settings schema, one detection/health strategy, one launch contract, one proof
gate set, and one rollback path. The least risky architecture is not to copy upstream repositories into
Hermes. Instead, Hermes should fetch and pin upstream repos or official release artifacts, lock them by
commit/tag/checksum, install them into isolated runtimes, and expose them through a single app-
manager API and CLI. That aligns with how the upstream projects themselves are distributed and licensed,
and it avoids the common failure mode where the UI “knows about” tools that the backend cannot actually
provision. 
The highest-confidence upstream map is clear for the core slicer , modeler , print-farm, firmware, generation,
and agent stacks: prusa3d/PrusaSlicer, SoftFever/OrcaSlicer, Flsun3d/FlsunSlicer, 
Ultimaker/Cura, Ultimaker/CuraEngine, supermerill/SuperSlicer, slic3r/Slic3r,

Current-state diagnosis
The uploaded archive and the screenshots do not describe the same implementation state. The uploaded
codebase still centers on an older tab set such as Dashboard, Agents, Workflows, 3D Generation,
Blender MCP, Slicing, Printer Fleet, Print Queue, Printer Control, Docked Apps, 
Proof & Reports, System Logs, and Settings. It also contains explicit mock-only language in the
settings tab and a small live bridge surface. The screenshots, however , show a different top shell with 
Source OS, Dashboard, Autopilot, Design, 3D Generation, Jobs, Printers, Observe, 
Voice, Agents, Learning, Artifacts, Approvals, Plugins, Settings, and Roadmap, plus
a Source OS sub-shell with 58 visible modules across 11 categories. In other words, the UI in the
screenshots outpaced the runtime contract present in the archive.
A second gap is scope coverage. The archive already contains partial adapter work for a small subset of
tools, but not the full screenshot inventory. It includes adapter schemas for PrusaSlicer , OrcaSlicer , FLSUN
Slicer , Cura, Moonraker , OctoPrint, Printrun, Blender , and Blender MCP , while only some adapter classes
exist for Fluidd and Mainsail. That explains why a visible app card can exist without a complete install/
detect/launch path. The GUI card count is larger than the registry count, and the registry count is larger
than the live bridge count. Until those three inventories are reconciled, the product will continue to display
cards that cannot actually be installed, detected, or launched.
A third gap is settings and truth. The screenshots make the product look like a controlled OS with proof,
approvals, launch modes, and provider selection, but the uploaded kit still leaves many of those paths
either mocked, read-only, or absent. The missing primitives are not “just buttons.” They are:
a manifest registry for every visible module
a per-app settings drawer generated from JSON Schema
a secret store for API keys and tokens
a model/provider registry for local and remote LLMs
installers with logs, checksums, and rollback
launch orchestrators for desktop, web, service, firmware, and library-type modules
proof gates that decide whether an action is safe, reproducible, and attributable
That is why the right answer is a complete contract kit, not a piecemeal patch.

Agents and orchestration
The most effective orchestration model is a staged, dependency-aware graph.
catalog-agent
Builds the visible inventory from manifests and keeps card metadata synchronized with the UI.
fetch-agent
Fetches locked release artifacts or repos, verifies checksums/signatures, and populates the local cache.
build-agent
Builds source-based modules inside hermetic containers and emits artifacts plus SBOMs.
configure-agent
Applies settings schemas, secret bindings, endpoint registration, printer host mappings, and model/

Security and compliance checklist
The screenshots and archive clearly imply secrets, API endpoints, and model routing. Production-grade
behavior requires the following.
Secrets:
no raw keys in the repo
no raw keys in screenshots, logs, bundles, or telemetry
vault or OS keychain storage only
secret refs, never secret values, in manifests
Providers and models:
provider adapters must declare scopes and data egress policy
LM Studio and Ollama should be first-class local providers because they expose local serving
endpoints and SDKs; remote providers such as DeepSeek and MiniMax must be explicit opt-in and
clearly tagged as cloud egress paths 
Licensing:
AGPL/GPL apps may be launched, embedded, or proxied, but redistribution and bundling strategy
must remain compliant
Bambu Studio explicitly notes a non-free networking plugin, so Hermes should treat that plugin as
optional and separable from the open core
