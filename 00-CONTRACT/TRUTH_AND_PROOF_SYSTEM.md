# TRUTH AND PROOF SYSTEM

> A claim made by Hermes3D-OS Lite — that a print is safe to dispatch,
> that a slicer profile validates, that an acceptance test passed — is
> only as trustworthy as the evidence behind it. This document defines
> how that evidence is produced, signed, and verified.

---

## 1. The two-level mental model

Hermes3D-OS distinguishes two levels of confidence:

| Level | What it means | Generated by |
|-------|---------------|-------------|
| **Truth Gate** | A check that *can* fail. Runs at decision time. Returns PASS or FAIL with reasons. | `core.validation.truth_gate` |
| **Proof Envelope** | A signed, append-only record of *what happened* and *what evidence supports it*. Reproducible from the inputs. | `core.proof.proof_envelope` |

A truth gate answers "is this safe right now?". A proof envelope answers
"can I show, six months from now, exactly which decision was made and
why?".

---

## 2. Truth gates (eight checks)

Every print-related decision passes through eight gates before it can
proceed. The gates are defined in `core.validation.truth_gate` and
applied in this order:

1. **Schema gate** — every input dataclass parses cleanly; all required
   fields populated; types match.
2. **Geometry gate** — the mesh is watertight (or annotated as
   intentionally non-watertight, e.g., a vase mode print); bounding-box
   extents are positive; no NaN vertices.
3. **Bed gate** — the part fits within the selected printer's bed shape
   and Z height; for delta beds, the xy-circle radius is checked, not
   just the bbox corners.
4. **Material gate** — the material is supported by the selected
   printer (e.g., PA-CF needs a hardened nozzle; ASA needs an
   enclosure).
5. **Skill gate** — no high-confidence failure-pattern skill predicts
   imminent failure for this printer/material combination.
6. **Spool gate** — there is enough filament loaded (or available to
   swap) to complete the print, with margin.
7. **Health gate** — the printer is online, in `ready` or `idle`
   klippy_state, and not currently printing something else.
8. **Workflow gate** — the upstream nodes in the print workflow have
   produced the expected outputs (e.g., `slicer_metadata` is present
   before dispatch).

A truth gate result is a `TruthGateReport`:

```python
@dataclass
class TruthGateReport:
    pass_: bool
    checks: list[TruthCheck]   # one entry per gate, with reason
    fingerprint: str           # hash of inputs, used by proof envelope
```

A truth gate is **not** a recommendation system. It cannot be silenced
or overridden silently. Calling code that wants to proceed despite a
FAIL must explicitly pass `force=True`, and the proof envelope records
that override.

---

## 3. Proof envelopes

A proof envelope is an HMAC-signed JSON document that records:

1. **What was decided** — the dispatch decision, slicer outputs, or
   acceptance result.
2. **What inputs produced it** — content-addressed by SHA-256 hashes of
   every relevant file (mesh, slicer config, klipper config).
3. **What gates passed** — the full TruthGateReport.
4. **What environment produced it** — git commit, Python version, host
   fingerprint.
5. **What time it was produced** — ISO 8601 UTC timestamp.

The signature is HMAC-SHA256 over a canonicalised JSON encoding of the
above (sorted keys, no whitespace, UTF-8). The signing key comes from
`HERMES3D_PROOF_KEY` (default `"hermes3d-default-proof-key-not-secret"` in
development, mandatory rotation in production).

Anatomy:

```json
{
  "envelope_version": "1.0.0",
  "produced_at": "2026-04-29T17:43:21Z",
  "produced_by": {
    "tool": "hermes3d.acceptance.run_acceptance",
    "git_commit": "abc1234",
    "python": "3.11.9",
    "host_fingerprint": "...sha256..."
  },
  "subject": {
    "kind": "acceptance",
    "variant": "compact",
    "printer_id": "flsun_t1_a"
  },
  "inputs": {
    "stl_sha256": "...",
    "slicer_config_sha256": "...",
    "klipper_config_sha256": "..."
  },
  "decision": {
    "pass": true,
    "checks": [...]
  },
  "signature": {
    "algorithm": "HMAC-SHA256",
    "value": "base64..."
  }
}
```

---

## 4. Verification

Any envelope can be verified by anyone who has the signing key:

```bash
hermes3d proof verify path/to/envelope.json
```

This recomputes the HMAC, recomputes the input SHA-256s (if the
referenced files are still on disk), and reports any mismatch. The
verifier is read-only — it never modifies the envelope.

The acceptance runner also offers a batch verifier:

```bash
python 03-PROOF-SYSTEM/conformance_runner.py --verify
```

which checks every envelope under `var/acceptance-results/` and exits
non-zero if any fail.

---

## 5. Tamper resistance

Every envelope is **append-only relative to its decision**. The signing
includes both the inputs and the decision; you cannot rewrite the
decision after the fact without invalidating the signature.

What the envelope is **not**:

- It is not a notarisation service. Anyone with the key can sign new
  envelopes; if you need third-party attestation, layer a sigstore /
  TSA on top.
- It is not encryption. The contents are clear-text JSON. Anyone with
  read access to the file can see the decision and inputs.
- It does not replace SBOM or supply-chain attestation for the
  software itself — that's a separate concern handled in the release
  pipeline (Layer E).

## 6. Where envelopes live

| Source | Path |
|--------|------|
| Acceptance test runs | `var/acceptance-results/<variant>/<printer_id>/proof.json` |
| Production print decisions | `var/proofs/dispatch/<job_id>.json` |
| Slicer runs | `var/proofs/slicer/<job_id>.json` |
| Truth gate fingerprints (audit log) | `var/proofs/gates/<date>.jsonl` |

All paths are configurable via environment variables documented in
`env/.env.example`.

---

## 7. Honesty interaction

The truth-and-proof system is the technical backbone of the honesty
ledger. The ledger asserts which features are runnable; the proof
system can be queried to *demonstrate* that runnable features still
produce verifiable outputs.

A claim that lacks a proof envelope is, by contract, a `spec` claim —
not a `runnable` one. Annotating runnable code as such requires a test
that produces a verifiable envelope.

This is the structural reason it is harder to lie in this codebase than
to tell the truth.
