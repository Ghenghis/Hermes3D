# SECURITY — Hermes3D-OS Lite

> Threat model, risky surfaces, and the rules every contributor follows
> to keep them safe.

---

## 1. Threat model — what we're defending against

This is a single-tenant, on-premises system that controls real-world
hardware (3D printers with hot ends, heated beds, and an ability to
move stepper motors into walls). The threats we explicitly take
seriously:

| Threat | What it looks like | Mitigation |
|--------|--------------------|------------|
| **Printer commanded to do something dangerous** | A request fires `M104 S350` or moves the head past `position_max` | Truth gates; Klipper's own bounds; no "raw G-code" tool exposed via REST/MCP without a confirm step |
| **Untrusted mesh corrupts runtime** | A specially-crafted STL crashes trimesh or the slicer | mesh_analyze runs first; non-watertight or NaN-vertex meshes are rejected before slicing |
| **Untrusted skill pack overrides safety** | A malicious `.skillpack` lowers a printer's `max_print_speed_mm_s` after install | Skill packs are SHA-256-verified; importer requires user confirmation; safety params are read-only outside the printer profile |
| **Remote-control bridge spoofed** | Someone fakes a Telegram/Discord control message | Per-channel allowlist of chat IDs; HMAC-signed action tokens for sensitive commands |
| **Secrets leaked into git** | API keys, bot tokens committed | `.env` gitignored; `env/.env.example` placeholder only; CI gitleaks scan |
| **Proof envelope tampering** | Someone rewrites a dispatch decision after the fact | HMAC-SHA256 over canonical JSON; verifier flags any mismatch |

What we explicitly do **not** defend against (out of scope for v5):

- Multi-tenant isolation. Hermes3D-OS Lite is for one farm operator.
- Network-attacker-in-the-middle on the LAN. Use a VPN or wireguard.
- Side-channel attacks on the proof key. The key lives in env, not in
  a TPM or HSM.
- Adversarial machine-learning inputs. We do not run user-trained
  models on user-supplied data.

## 2. Risky surfaces — enumerated and mitigated

### 2.1 Slicer execution

`core.slicer.slicer_runner` invokes PrusaSlicer or OrcaSlicer as
external processes. Mitigations:

- The mesh path passed to the slicer is validated by
  `mesh_analyze` first.
- The slicer config is generated by
  `core.slicer.profile_generator` from typed profiles, never
  concatenated from user strings.
- The slicer process runs with a timeout (default 600 seconds).
- Slicer stdout/stderr is captured and logged; non-zero exit codes
  fail the workflow.

### 2.2 Moonraker control

`core.printers.moonraker_client` POSTs to `gcode/script` and `printer/print/start`. Mitigations:

- Every command goes through truth gates first.
- Moonraker's own API key auth is supported via env
  (`HERMES3D_MOONRAKER_API_KEY` per printer in `printers.toml`).
- Bound checks: target temperature ranges, max acceleration, max speed
  are clamped to printer-profile values before the command is sent.
- A "dry-run" mode is available for every operation.

### 2.3 Remote-control bridge (opt-in)

`core.integrations.remote_control` listens for Telegram updates and
Discord webhook events. Mitigations:

- Disabled by default. Requires explicit env vars to start.
- Allowlisted chat IDs only — set in `config/remote_control.toml`.
- Sensitive commands (cancel print, run macro, change temperature)
  require a HMAC-signed token re-derived from the user's chat ID and
  a server-side secret.
- All actions log to `var/proofs/remote/<utc>.json` with a signed
  envelope.

### 2.4 Tool registry

`core.agents.tool_registry` exposes 11 tools to LLM agents. Tools that
mutate state (queue_add, calibration, dispatch) are gated:

- `queue_add` requires a SHA-256 of the mesh — not a path the LLM
  could fabricate.
- `calibration_macro` is **read-only** in v5 (returns the macro that
  *would* be sent). Actually firing the macro requires a separate
  call into `core.agents.calibration.run_calibration()` which is not
  exposed via the registry.
- `dispatch` is a planning operation only — it does not start a print.

### 2.5 Skill packs

`core.memory.skill_pack` accepts JSON bundles signed with HMAC.
Mitigations:

- Importer rejects unsigned packs.
- Importer rejects packs whose SHA-256 disagrees with the manifest.
- Importer prompts the user before applying any skill that would lower
  a safety parameter (max temperature, max speed, max accel).

### 2.6 Vector memory

`core.memory.vector_memory` builds a TF-IDF index over user-supplied
text (skills, notes). The optional FAISS path uses local embeddings
only — no model is downloaded at runtime without explicit consent.

## 3. Secrets management

| Secret | Where it lives | Where it must NOT live |
|--------|----------------|-------------------------|
| Moonraker API keys | `config/printers.toml` (per printer) or env | git |
| `HERMES3D_PROOF_KEY` | env, set per machine | git, code |
| Telegram bot token | env (`HERMES3D_TELEGRAM_BOT_TOKEN`) | git, code |
| Discord control webhook | env (`HERMES3D_DISCORD_CONTROL_WEBHOOK`) | git, code |
| LLM provider keys (OpenRouter etc.) | env | git, code |

`env/.env.example` lists every variable name. `.env` itself is
`.gitignored`.

CI runs `gitleaks` (or equivalent) against every commit. New secret
patterns are added to `.gitleaks.toml` as the project evolves.

## 4. Reporting a vulnerability

If you find a security issue:

1. Do **not** open a public GitHub issue.
2. Email the maintainer directly with subject `[hermes3d security]`.
3. Include:
   - Affected version (commit hash if possible)
   - Reproduction steps
   - Impact assessment (what an attacker could do)
   - Suggested fix, if you have one

You should expect an acknowledgment within 72 hours and a remediation
plan within two weeks.

## 5. Hardening checklist (deployment)

Before running Hermes3D-OS Lite as a daily driver on a network where
other people can reach it:

- [ ] `HERMES3D_PROOF_KEY` set to a strong random value (≥32 bytes).
- [ ] `.env` permissions are owner-read-only (`chmod 600`).
- [ ] Moonraker instances behind a VPN or LAN-only firewall rule.
- [ ] Gradio launcher bound to `127.0.0.1`, not `0.0.0.0`.
- [ ] REST API behind a reverse proxy with TLS if exposed beyond
      localhost.
- [ ] Remote-control bridge allowlist populated; HMAC token secret
      different from the proof key.
- [ ] `pip-audit` clean on the production environment.

## 6. Auditable log of what happened

Every dispatch decision, slicer run, calibration intent, and remote
control action produces a signed proof envelope. To inspect:

```bash
python 02-SCAFFOLDING/scripts/proof-collect.sh
cat var/proof-report.json | jq '.summary'
```

Tampering with the JSON files invalidates the HMAC. The verifier exits
non-zero and lists every failed envelope.
